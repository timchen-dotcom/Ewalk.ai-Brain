# 2026-05-31 前三名 Repo 導入紀錄

## 導入目標

依提姆先生指示，將 GitHub AI repo 候選前三名導入 Ewalk.ai，並開發成三個能用的 AI 工具。

前三名：

1. [crawl4ai](https://github.com/unclecode/crawl4ai)
2. [browser-use](https://github.com/browser-use/browser-use)
3. [Dify](https://github.com/langgenius/dify)

## 導入策略

第一版不全量安裝大型 repo，而是先做可控 MVP：

- 保留 repo 的核心用途與工具定位。
- 用本地 Node CLI 做可執行工具。
- 使用現有 `OPENAI_API_KEY` 呼叫 OpenAI Responses API。
- 不自動修改客戶網站、Google 商家、Make、Dify 或任何正式後台。
- 後續若 PoC 通過，再正式接入原 repo 或服務。

## 已完成工具

### 1. 官網與 Google 商家 AI 健檢

導入來源：crawl4ai

本地工具：

```text
Ewalk.ai Brain/08_自動化/AI工具實驗室/tools/website-audit.mjs
```

用途：

- 抓取客戶官網公開內容
- 產出 SEO 優化建議
- 產出 Google 商家產品 / 服務 / 貼文建議
- 檢查 CTA、預約流程與內容缺口

### 2. 瀏覽流程 AI 健檢

導入來源：browser-use

本地工具：

```text
Ewalk.ai Brain/08_自動化/AI工具實驗室/tools/browser-flow-audit.mjs
```

用途：

- 分析網站轉換路徑
- 檢查 CTA、表單、連結與預約入口
- 產出瀏覽流程改善建議
- 標記需要真實瀏覽器測試的事項

### 3. Dify 風格 AI Workflow 產生器

導入來源：Dify

本地工具：

```text
Ewalk.ai Brain/08_自動化/AI工具實驗室/tools/workflow-builder.mjs
```

用途：

- 將 AI 工具需求轉成 Dify 風格 workflow 規格
- 產出輸入欄位、節點流程、Prompt、輸出格式與測試案例
- 方便後續交給 Dify / 工程 / 自動化專員落地


## 目前限制

在目前 Codex 沙盒環境中，外網與 OpenAI API 連線會失敗：

```text
OpenAI API 連線失敗：fetch failed
```

另外，直接抓取公開網站時也可能被 DNS / 網路限制擋住。

判斷：

- 工具本地流程可執行。
- AI 產出與真實網站抓取需要在一般終端機、部署環境或解除網路限制後測試。
- 第一版已保留 `--no-ai` 模式，可先測格式與流程。

## 後續建議

1. 在一般終端機執行一次 TheVision 官網健檢。
2. 若成功，將輸出報告接回 TheVision 官網改版任務。
3. 若 Google 商家健檢工具要正式產品化，先以 crawl4ai + workflow-builder 跑 3 個客戶樣本。
4. browser-use 真正導入前，先定義權限邊界：只能測試，不自動發布、不登入金流、不改廣告預算。
5. Dify 若要正式使用，需確認 Dify Cloud 或自架方案。
