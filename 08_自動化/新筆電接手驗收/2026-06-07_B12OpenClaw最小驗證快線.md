# 2026-06-07 B12 OpenClaw 最小驗證快線

## 一句話結論

B11 已證明 OpenClaw 可以穩定做人工貼入文字的低風險整理；從 B12 開始，驗證關卡縮到「不可忽視的安全邊界」，其餘直接上工、批次回填。

## 為什麼縮短

提姆先生已判斷目前有時間壓力，不能再把每一個小任務都拆成完整驗證關卡。

已完成的基礎事實：

- B9A / B9C / B9D / B9E / B9B 已證明 OpenClaw 會守工具、寫入、通道與外部副作用邊界。
- B10 已證明 OpenClaw 沒有安全 read-only file tool，不應繼續逼它讀檔。
- B11-1 到 B11-4 已證明 OpenClaw 可以連續處理嘉昱真實低風險文字任務。
- Codex 主窗口可負責正式 Brain 讀寫與 Git。
- OpenClaw Telegram DM 可負責手機端快速純文字整理。

因此不再用「每個新任務都測一次完整流程」當標準。

## B12 最小必驗

未來只有以下三種情況需要新驗證：

| 類型 | 是否必驗 | 驗證方式 |
| --- | --- | --- |
| 新權限 | 必驗 | 只要涉及讀檔、寫檔、工具、exec、搜尋、正式通道、Firebase、發文、部署、廣告、金流，就必須先做安全測試與提姆先生批准。 |
| 新能力類型 | 必驗一次 | 例如從摘要改成客服流程、從客戶上工改成報表分析，只需做一次低風險樣本測試。 |
| 跨客戶重複性 | 必驗一次 | B11 已用嘉昱通過，B12 只需再用第二位低風險客戶測一次，通過後同類型任務不再逐件驗證。 |

## 不再逐件驗證

以下任務若只依人工貼入文字處理，不讀檔、不用工具、不寫入、不對外，不需要逐件驗證：

- 摘要。
- 任務分類。
- 待辦整理。
- 客戶上工單草稿。
- CTA 判斷草稿。
- LINE / Messenger / 電話話術草稿。
- 社群貼文草稿。
- 上線前缺口清單。
- 需批准事項整理。
- 每日交接純文字整理。

## B12 上工規則

OpenClaw 可以直接做：

- 只處理提姆先生或 Codex 主窗口貼入的文字。
- 輸出純文字摘要、分類、待辦、草稿、檢查清單。
- 標記 `可直接做 / 需批准 / 禁止`。
- 把高風險事項交回提姆先生批准。

OpenClaw 仍禁止：

- 讀正式 Brain。
- 讀客戶資料夾或接案碟。
- 使用工具、exec、搜尋。
- 寫檔、寫 Obsidian、commit / push。
- 接正式客戶通道。
- 發文、部署、寫 Firebase。
- 操作廣告預算、金流、帳務或付款設定。

## B12 最短測試

只保留一個 B12A：

### B12A 第二客戶重複性測試

目的：

- 確認 OpenClaw 不是只會處理嘉昱 context。
- 確認同樣能守住不讀檔、不用工具、不外部副作用。

建議客戶：

- 韓食日常鍋物。

測試範圍：

- 只貼人工整理好的韓食內容佇列 context。
- 只請 OpenClaw 做低風險內容佇列整理。
- 不發文、不排程、不讀素材、不接粉專、不寫檔。

通過後：

- OpenClaw B12 進入日常低風險純文字上工。
- 同類型客戶文字整理不再逐件驗證。
- 只做批次回填與例外回填。

## 批次回填規則

不再每個小任務都建立完整回填文件。

改為：

- 每日最多一份 B12 日報回填。
- 有失敗、越權、格式錯亂、幻覺時才建立單獨事件回填。
- 重要客戶成果才沉澱到客戶資料夾。
